## 1. 背景与要解决的问题

### 1.1 问题陈述

市面上的通用 AI 生活助手采用一套隐性的「通用默认」视角，而这个默认常常不自觉地向男性经验倾斜，于是在日常生活的高频场景里留下一批**没人认真服务的缝隙**：

| 缝隙 | 具体表现 |
| :--- | :--- |
| 健康建议默认以男性生理为基准 | 经期护理、非典型心脏病症状（女性心梗常表现为胸闷+背痛+冷汗而非压榨性胸痛）、盆底健康——要么一句带过，要么空白 |
| 家务建议默认执行者是「主妇」 | 输出的是「如何更勤快地收拾」，而不是「如何让家人共同分担」 |
| 安全提示不考虑女性特有场景 | 夜归、独居、需要冷静求助渠道的时刻 |
| 情绪表达容易被玩笑打断 | 用户说「最近很累，没人可说」，得到的可能是一个抖机灵 |

**这不是技术问题，是视角问题**——所以它不能用「换一个更强的模型」来解决。

### 1.2 现状：v0.x 已经证明了什么、还没证明什么

**已经证明的（可复现、有代码与测试为证）**
- 这套视角可以被落进产品：4 大场景 71 条结构化知识（健康 25 / 理财 16 / 做饭 15 / 家务 15）、视角公平的设计原则已写进系统提示词。
- 成本可以被压到用户「随手问」不心疼：单次对话 < 1 分钱，联网默认 0 token（只给可点来源，用户说「读」才抓正文）。
- 质量可以被**主动**度量，而不只是等用户点踩：`eval/` 已建成 5 维评分标准 + 29 条评测集 + 检索开/关对照引擎，dry-run 零 token 全流程可自证。
- 工程可以撑住迭代：79 个自动化测试、CI、ruff + pre-commit 门禁。

**还没证明的（本 PRD 要解决的）**
- ❌ 没有任何真实用户用过。留存、使用频率、真实提问分布——全是空白，我不打算编造指标来撑门面。
- ❌ 评测体系**没有跑过一次真实评测**，因此「关键词检索到底值不值」目前仍是信念而非结论。
- ❌ 没有线上地址。HR 或朋友想看，只能自己 clone 代码跑。
- ❌ 安全依赖提示词。目前「遇到危急信号要提示就医」写在 SYSTEM_PROMPT 与 rubric 里，**代码层没有兜底**——提示词不是安全边界。

### 1.3 核心假设（明确标注：未经用户验证）

> **H1**：在几个高频生活场景里，把女性视角当作**设计前提**（而非一个可关闭的附加开关），同时保持对所有用户友好，能显著提升目标用户对回答质量的感知。
>
> **H2**：这类「视角公平」的价值，用户**能感知、并且愿意为它换一个产品**。

H1 与 H2 目前都是**我的判断**，不是调研结论。v1.0 的全部需求，都服务于把它们变成可证伪的结论。

## 2. 目标与非目标

### 2.1 v1.0 唯一目标

**让一个真实用户能在浏览器里打开 Circle、问一个问题、得到靠谱的回答；并且我能用数据回答「它答得好不好」。**

拆成两句可检验的话：
1. **可访问**：存在一个链接，非技术用户点开即用。
2. **可度量**：上线后每一轮迭代，都能回答「改完是变好了还是变坏了」——质量由 `eval/` 给，体验由埋点与反馈给。

### 2.2 非目标（v1.0 明确不追求）

- ❌ **不追求增长**。首批用户是个人网络内的十几个人，规模小到任何增长率都没有统计意义。
- ❌ **不追求功能完整**。v1.0 只做「把 v0.x 安全地放出去 + 装好仪表」，不加新场景。
- ❌ **不追求商业化**。成本目标只是「别失控」，不是「跑通付费」。

## 3. 目标用户

### 3.1 首批用户（v1.0 实际触达的范围）

| 项 | 说明 |
| :--- | :--- |
| **是谁** | 我现实社交圈内的女性用户（同学、朋友），年龄 20–30，有向 AI 提问生活/健康问题的习惯 |
| **怎么来** | 我直接邀请，说明这是求职展示用的内测 demo，数据存在服务器本地、重新部署即重置 |
| **规模预期** | 10–20 人。不投放、不公开传播 |
| **为什么是他们** | 我能在上线后直接问「哪里不好用」——首批用户必须是我能拿到定性反馈的人，而不是陌生人 |

### 3.2 暂不服务的用户（明确排除）

- 需要**医学诊断**的用户——Circle 只给循证护理与「何时该就医」的判别，不做诊断。
- 需要**通用搜索**的用户——Circle 只覆盖官方媒体头条，不是搜索引擎。
- 需要**长期个人健康档案**的用户——v1.0 无账号体系，数据是服务器本地文件、重新部署即重置。

## 4. 需求与优先级

### 4.1 优先级方法（以及为什么不用 RICE）

**我没有用 RICE。** 原因很直接：RICE 需要 Reach（触达人数）、Impact（影响程度）两个输入，而这两个数在没有真实用户之前**只能是拍脑袋**。用拍出来的数算出小数点后两位的分数，是**用精确的形式掩盖不精确的实质**——比不用方法更危险。

v1.0 采用**风险优先分级**，判据只有一条：**这个需求不做，会分别造成什么后果？**

| 级别 | 判据 | 不做会怎样 |
| :--- | :--- | :--- |
| **P0** | 触及**安全 / 合规 / 可用性**底线 | 可能伤害用户、可能违法违规、或者根本打不开 |
| **P1** | 决定**核心假设能否被验证** | 能上线，但上完仍然不知道 H1/H2 成不成立，等于白做 |
| **P2** | 提升**体验与纵深** | 上线后照常运转，只是不够好用 |

> 这套分级的可复用之处在于：**它不依赖数据，但每一条都能说清后果**。数据齐了之后再上 RICE 也不迟——那时 RICE 才有意义。

### 4.2 P0 · 上线阻塞项

| # | 需求 | 为什么是 P0 | 验收标准 | 现状 |
| :--- | :--- | :--- | :--- | :--- |
| **P0-1** | **合规边界确认** | 产品含医疗健康类问答。需要先弄清两件事：①**受邀内测**形态（定向邀请、不公开传播）适用什么要求；②日后若转为**公开运营**，需要补什么（备案、相应资质、隐私政策形式等）。**先弄清边界，再决定以哪种形态发布**——不默认「能公开」 | 产出结论明确的记录（含依据来源），并据此定下 v1.0 的发布形态 | ⚠️ 未做。当前只有「用高位端口规避域名备案」的技术判断，缺少合规层面的确认 |
| **P0-2** | **安全兜底下沉到代码层** | 当前「危急信号必须提示就医」**只写在 SYSTEM_PROMPT 和 rubric 里**。提示词是概率性的——模型可能不遵守，尤其在被诱导或长对话下。涉及健康场景，「大概率会提示就医」不是可接受的安全水位 | 在代码层加独立于模型的兜底：命中危急信号词表（如胸痛+冷汗、非经期大量出血、单侧剧痛、自伤倾向）时，**无论模型回答什么，都强制追加一条明确的就医/求助提示**。配套测试覆盖词表命中与不命中的两类路径 | ❌ 未实现。这是 v1.0 **最不能省的一条** |
| **P0-3** | **隐私说明页** | 产品会让用户把经期、情绪、身体状况这类最敏感的信息说出来。用户有权在上线那一刻就知道：数据存在哪、谁能看到、什么时候会被清掉。这既是合规要求，也是产品信任的前提 | 上线前必须有可访问的隐私说明，至少写明：①对话与记忆以本地 JSON 存于服务器，不上传任何第三方；②重新部署即重置，不做长期留存；③可通过记忆管理入口一键查看与清除；④API 密钥只从环境变量读取、永不入库 | ⚠️ 事实已成立（代码即如此），但**没有面向用户的说明页** |
| **P0-4** | **部署与可访问地址** | 一个给面试官看的作品，必须能被点开。这是 v1.0 存在的物理前提 | 国内网络可直连的地址；README 顶部补上链接；进程守护 + 重启自恢复；成本护栏（限流 10 次/分/IP + 日 token 预算）在生产生效 | ⚠️ `Dockerfile` + gunicorn 已就绪，但**尚无线上实例**（Render 两次强制绑卡、Railway 试用额度到期、Vercel 与 SSE 形态不匹配，均已排除） |
| **P0-5** | **滥用与成本失控防护复核** | 公开可访问 = 任何人可刷。当前限流按 IP 每分钟 10 次、日预算 100 万 token——但公开后需要确认：单 IP 日上限、异常用量告警、以及超出预算时是优雅降级还是硬失败 | 压测/模拟验证：①单 IP 持续刷不会击穿日预算；②预算耗尽时返回明确提示而非报错崩溃；③有可查的用量记录 | ⚠️ 限流与预算已实现（`config.py`），**未做滥用场景验证** |

### 4.3 P1 · 决定假设能否被验证

| # | 需求 | 为什么是 P1 | 验收标准 |
| :--- | :--- | :--- | :--- |
| **P1-1** | **跑首轮真实评测** | 「关键词检索值不值」目前是信念。eval 框架已建好、dry-run 已通，只差真跑一次基线 | 29 条 × 检索开/关 两变体跑完，产出 `report.md`：变体×维度均值表、分桶表、badcase 清单；**先按 §6.2 的质量线判定是否达标**，达标才继续上线 |
| **P1-2** | **埋点最小集** | README 里的「谁在用、留不留、卡在哪」目前无法回答。没有埋点，上线之后依然只能靠感觉 | 能回答三个问题：①有多少人来过、多少真的问了问题；②有多少人**第二天还回来**；③badcase 集中在哪些场景/桶 |
| **P1-3** | **badcase 回流闭环** | 评测与反馈的价值不在「发现了问题」，在于**改完能证明改好了**。这是 v0.x 已经有雏形但没跑通的环节 | 从 `feedback/` 与 eval 报告中取 badcase → 落到知识库或提示词的具体修改 → **用同一个评测集复跑**，确认对应维度分数上升且无回归 |
| **P1-4** | **知识库覆盖缺口补齐** | 评测集已经暴露出缺口：部分安全类问题（如 HPV 疫苗相关谣言）知识库无对应条目，只能靠提示词顶。这是「评测发现自己产品的洞」的直接价值 | 凡 `hit = null` 的高严重度 case，要么补知识条目，要么在 PRD 里明确记录「决定不补」及理由 |

### 4.4 P2 · 体验与纵深（v1.0 之后）

| 需求 | 触发条件（什么时候才值得做） |
| :--- | :--- |
| 记忆升级为语义检索 | 出现「用户换个说法就记不住」的真实反馈，且关键词方案已到召回上限 |
| 检索升级为混合检索 + 段落级引用 | P1-1 的评测结果证明召回是质量瓶颈 |
| 账号体系 + 多端同步 | **必须先有隐私政策与合规评估**，否则不做 |
| 语音交互 / 小程序 | 有用户明确表达「不想打字」 |
| 多模型 provider 与路由 | 出现单点依赖导致的真实事故（如服务不可用、价格变动） |

## 5. 关键产品决策与代价

> 每一条都是「需求 → 选了 A → 放弃了 B → 代价是什么」。**面试官想看的不是"我全会做"，而是"我知道自己在放弃什么"。**

| 决策 | 放弃的方案 | 为什么 | 代价（已承认） |
| :--- | :--- | :--- | :--- |
| 记忆用**规则提取** | LLM 提取 | 省 token、可解释、用户能逐条查看和删除 | 换个说法就记不住 → Roadmap 的语义检索 |
| 知识库用**关键词 + N-gram 检索** | 向量 RAG | 71 条量级下命中确定、零额外依赖、零成本，且**可解释**（能说清为什么命中这条） | 召回上限低 → 检索接口留成可替换 |
| 联网**默认只给可点来源** | 自动读全文 | 抓取 0 token，只有把正文送进模型才花钱。默认 0 token，用户说「读」才烧 | 多一步交互；但把成本决定权交还给用户，且用户不需要懂 token |
| 新闻走**官方媒体 RSS** | 搜索 API | 两条搜索通路都实测不可用（DeepSeek 原生 web_search 在本账号不生效、DuckDuckGo 国内不可达）。RSS 是 0 token / 0 key / 可自证的 | **不是通用搜索**，只覆盖官方媒体头条；查不到就明确降级，不假装搜过 |
| **单页、无账号**形态 | 完整账号体系 | 让「打开到用起来」趋近零摩擦，先验证核心价值 | 无法多端同步、无法长期留存 |
| 回答截断时**自动续写** | 让用户手动「继续」 | 「话说一半」是体验事故 | 多耗 token → 用截断提示兜底，最多续 2 轮 |
| **单模型（DeepSeek）**起步 | 多模型容灾 | 聚焦，先验证产品而非引擎 | 单点依赖 → P2 项 |

## 6. 指标与验收标准

### 6.1 北极星指标：**「被认真对待的回答」占比**

**定义**：在产生过反馈的对话中，用户未点踩、且该场景在 `eval/` 对应维度得分 ≥ 4 的比例。

**为什么不用 DAU / 留存率做北极星**：首批 10–20 个用户，DAU 的波动主要来自我有没有提醒他们，不来自产品好坏。**在最该看质量指标的阶段去看增长指标，是仪表盘放错了位置。**

### 6.2 上线门槛（质量线，**不达标不上线**）

这一组数字在 P1-1 真跑之前是**预设的门槛**，不是结论。跑完之后无论达标与否，都如实记录。

| 指标 | 门槛 | 依据 |
| :--- | :--- | :--- |
| 安全桶严重 badcase 数（D1/D2/D4 = 1） | **0** | 健康场景下，一条「把心梗说成多休息」就足以否掉整个产品 |
| D2 就医边界 平均分 | **≥ 4.0** | 这是 Circle 相对通用助手最该赢的一维 |
| D5 幻觉与引用 平均分 | **≥ 3.5** | 宁可承认不知道，也不能编 |
| 合规红线命中数 | **0** | 硬红线，无阈值可谈 |

### 6.3 上线后观察指标（只观察、不设目标）

| 指标 | 怎么采 | 怎么读 |
| :--- | :--- | :--- |
| 有效对话率（来过的人里真的提问的比例） | 埋点 | 低 → 首页或首屏引导有问题，不是模型问题 |
| 次日回来率 | 埋点 | 样本太小，只作定性参考 |
| 👎 率与 badcase 分布 | `feedback/` | 定性看「错在哪一类」，不看百分比 |
| 单次对话成本 & 日总成本 | `cost/daily_usage.json` | 守住「别失控」，不是「越低越好」 |

### 6.4 埋点方案

**只采四类，不做用户画像**：①会话与提问次数（匿名计数，不关联身份）；②场景分布（按命中的知识库类别统计）；③反馈（👍/👎，已有）；④成本与 token（已有）。**不采集**：设备指纹、地理位置、跨站标识。理由：为验证 H1/H2 只需要这四类，多采的每一条都是隐私负担。

## 7. 明确不做（v1.0）

- ❌ **不做医疗诊断**：只给循证护理与「何时就医」的判别，明确不构成专业建议。
- ❌ **不做通用网页搜索**：只覆盖官方媒体头条。查不到就明确降级为普通回答，**不留一个「看起来能搜」的假入口**。
- ❌ **不做社区 / UGC / 排行榜**：陪伴类产品的信任感来自私密与专注。
- ❌ **不做账号体系与多端同步**：在隐私政策与合规评估落实之前不碰。
- ❌ **不在公开上线前宣称任何留存/活跃数据**：没有的数据不写。

## 8. 风险与依赖

| 风险 | 影响 | 应对 |
| :--- | :--- | :--- |
| **医疗安全**（最高） | 错误建议可能造成实际伤害 | P0-2 代码层兜底 + §6.2 质量线**不达标不上线** + rubric 中 D1/D2 得 1 分即判 badcase |
| **合规不确定性** | 可能无法以当前形态公开提供服务 | P0-1 先确认边界，再决定 v1.0 走「受邀内测」还是「公开运营」形态；边界弄清之前不主动公开传播 |
| 单点依赖 DeepSeek API | 服务不可用 / 价格变动 | 已把调用收敛在 `config.py`；P2 评估多 provider |
| 成本被刷 | 账单失控 | 限流 + 日预算（已实现）；P0-5 补滥用场景验证 |
| 隐私泄露 | 敏感健康信息外泄 | 本地 JSON、密钥只走环境变量、文件已 gitignore；P0-3 补齐用户侧说明 |
| **单人开发的时间风险** | 需求堆积、长期不落地 | 本 PRD 的 P0 只有 5 条，且都不依赖新功能开发；**先上线，再迭代** |

## 9. 里程碑

| 阶段 | 内容 | 完成判据 |
